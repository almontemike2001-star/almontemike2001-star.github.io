01 · Batch

BeanFlow Coffee: a retail analytics platform

My first project, and the closest to my day job: a pretend 120-store coffee chain, from the POS database to the dashboards a manager would open on Monday. I wanted to build the whole chain myself once, including the boring parts like late updates and price history.

Decisions worth explaining

Replay-safe incremental loads

Extraction windows overlap on purpose so late updates are never missed. The silver layer then dedupes on primary key + updated_at, which keeps real history and drops replay copies.

SCD Type 2 without snapshots

Product and store history is rebuilt from source versions. Point-in-time joins mean margin uses the cost that applied when the order happened.

A complete denominator

A store-day calendar spine keeps open stores with zero sales in the data, so ADS and ADQ are never overstated.

Ratios recomputed, never averaged

AOV, ADS and margin % are stored as numerator and denominator, then recalculated at every level of aggregation.

02 · Streaming

PourStream: a streaming order-event pipeline

BeanFlow loads data in batches, so next I tried streams. Coffee-app orders go through Kafka, get checked against a data contract, and land in a Parquet lake. The interesting part was making the marts come out right when events arrive twice, hours late, or broken.

View source on GitHub Open the live KPI report See the dashboards

How the events flow

Select a stage to see what it does.

Messages streamed29,569one simulated week, 12 stores
Duplicates collapsed5351.8% of messages, none double-counted
Late events handled862arrived 20 min to 6 h after the event
Dead-lettered146rejected by the contract, kept for replay

Decisions worth explaining

At-least-once in, exactly-once out

Offsets are committed only after a batch is written, so a crash replays it instead of losing it. Silver keeps the first delivery of each event_id, so replays and client retries never double-count.

Late events correct the past

The incremental order fact rebuilds every order touched by new events from all of its events. A test proves the incremental table always equals a full rebuild.

A contract at the door

Every message must pass a typed Pydantic contract. Bad ones go to a dead-letter queue with the reason and raw payload, so nothing is silently dropped.

Dashboards as code

Gold marts are published to Postgres, and a script builds every Metabase question, filter and dashboard through the API, so the BI layer is versioned like the models.

03 · Change data capture

Hatid: a CDC lakehouse on ClickHouse

At work our data reaches ClickHouse through CDC, and I wanted to understand that path end to end, so I built a small version of it. It's a food-delivery app whose rows keep changing: orders update on the way to the door, customers delete their accounts, and a column gets added mid-run. Debezium captures each change from Postgres, Redpanda carries it to ClickHouse, and dbt rebuilds both current state and history.

View source on GitHub Open the live KPI report See the dashboards

How the changes flow

Select a stage to see what it does.

Change events39,964captured from Postgres
Updates replicated27,628orders change 4–5 times each
p95 replication lag3.3 sPostgres commit → ClickHouse
Tables in sync5/5row count and checksum match

Decisions worth explaining

Changelog plus current state

Every change is kept in an append-only changelog. Current state is a ReplacingMergeTree on the Postgres LSN, so the latest version wins and deleted rows drop out.

History without snapshots

Type 2 customer history and point-in-time restaurant ratings are rebuilt from the changelog, so each order carries the rating that applied when it was placed.

Schema changes while running

A tips column is added mid-run: ClickHouse first, then Postgres. The consumer pauses during the swap, so no message is lost.

Prove it arrived

Each run compares Postgres and ClickHouse with a checksum over every key and its last update time, so a missed update or delete fails, not just a missing row.

04 · Automation

Bantay: supplier document automation with n8n and an LLM

A lot of job posts now ask for n8n and AI automation, and I wanted to find out where an LLM actually helps and where it gets things wrong. Suppliers email certificates, insurance papers and invoices as PDFs. A rules parser and a small local LLM both read each one, and the result is only accepted when they agree and pass validation. Everything else goes to a person.

View source on GitHub Open the live KPI report See the screens

How a document is handled

Select a stage to see what it does.

Handled automatically81.4%315 of 387 documents
Automatic decisions correct315/315every field, vs ground truth
Unknown CRM outcomes46timeouts and 5xx, all resolved
Duplicates in the CRM0lookup before every retry

Decisions worth explaining

The LLM is never the only check

Business rules validate every result, and where the rules parser can read the layout, both readers must agree. Alone, the LLM got 84% of documents fully right; with the checks, nothing wrong was accepted automatically.

Let the model copy, let code parse

Forcing the small model to output ISO dates made it scramble digits. It now copies dates as printed, and code parses them with the document’s own format hint (US forms print MM/DD/YYYY).

Unknown means unknown

A timeout or 5xx from the CRM is not a failure. The worker searches the CRM for the record’s key, and retries only after two lookups confirm it never landed.

People stay in the loop

Documents that need judgement go to a review page with the reason, both readings and the PDF. Corrections pass the same validation before they are accepted.
