Project 1 · Batch analytics

BeanFlow Coffee: a retail analytics platform

An end-to-end analytics platform for a simulated 120-store coffee chain, from the POS database to executive dashboards. It covers both sides of the job: the engineering that makes the numbers correct, and the analysis that makes them useful. All data is synthetic.

Engineering decisions that keep the numbers right

Replay-safe incremental loads

Extraction windows overlap on purpose so late updates are never missed. The silver layer then dedupes on primary key + updated_at, which keeps real history and drops replay copies.

SCD Type 2 without snapshots

Product and store history is rebuilt from source versions. Point-in-time joins mean margin uses the cost that applied when the order happened.

A complete denominator

A store-day calendar spine keeps open stores with zero sales in the data, so ADS and ADQ are never overstated.

Ratios recomputed, never averaged

AOV, ADS and margin % are stored as numerator and denominator, then recalculated at every level of aggregation.

Project 2 · Streaming data

PourStream: a streaming order-event pipeline

BeanFlow is batch. PourStream covers the other half of data engineering: event streams. Coffee-app orders flow through Kafka, are checked against a data contract, and land in a Parquet lake. dbt then turns them into marts that stay correct when events arrive twice, hours late, or broken. All data is synthetic.

Engineering decisions that keep the stream honest

At-least-once in, exactly-once out

Offsets are committed only after a batch is written, so a crash replays it instead of losing it. Silver keeps the first delivery of each event_id, so replays and client retries never double-count.

Late events correct the past

The incremental order fact rebuilds every order touched by new events from all of its events. A test proves the incremental table always equals a full rebuild.

A contract at the door

Every message must pass a typed Pydantic contract. Bad ones go to a dead-letter queue with the reason and raw payload, so nothing is silently dropped.

Dashboards as code

Gold marts are published to Postgres, and a script builds every Metabase question, filter and dashboard through the API, so the BI layer is versioned like the models.

Project 3 · Change data capture

Hatid: a CDC lakehouse on ClickHouse

A synthetic food-delivery app whose database rows keep changing: orders update as they move to the door, customers delete their accounts, and a column is added mid-run. Debezium captures every change from Postgres, Redpanda carries it to ClickHouse, dbt rebuilds current state and history, and Dagster orchestrates it with replication checks. All data is synthetic.

Engineering decisions for data that changes

Changelog plus current state

Every change is kept in an append-only changelog. Current state is a ReplacingMergeTree on the Postgres LSN, so the latest version wins and deleted rows drop out.

History without snapshots

Type 2 customer history and point-in-time restaurant ratings are rebuilt from the changelog, so each order carries the rating that applied when it was placed.

Schema changes while running

A tips column is added mid-run: ClickHouse first, then Postgres. The consumer pauses during the swap, so no message is lost.

Prove it arrived

Each run compares Postgres and ClickHouse with a checksum over every key and its last update time, so a missed update or delete fails, not just a missing row.
